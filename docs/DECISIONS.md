| B40 | **Smart lists are not exported as lists.** An 'I' record with created-by 3 is a smart list ("Last Week" and "Last Month" in the Mac 4.8.13 sample; Garmin's Mac manual also lets users make their own from rules with File > New Smart List). It is left out of the tree, its item references place nothing, and the report says once, with a count, that smart lists were left out and that their items are saved in the user's own lists or in "Not in any list" (`smart_lists_left_out`). Why: a smart list is a filter that BaseCamp refills by itself; in the GFI it stores an ordinary reference for every item it showed at the last save, so in the Gate 1 sample exporting it wrote every item three times and marked all 14 as "in several lists". Nothing is lost: every item is still written once in its own list. Rejected: a "Smart lists" folder in the export (it repeats items and freezes a stale filter result). GUESS: user-made smart lists are also created-by 3 (not measured; FORMAT.md §15.9). The founder may prefer to keep the user's own smart lists; that needs a third Gate 1 run that makes one. | 2026-10-07 | mac48 implementation pass |
| B41 | **H-MAC48 is a third layout hypothesis and part of the supported path for file format 188** (FORMAT.md §15.11): 'W' = H-KBM + 8 opaque bytes; 'T' = H-KBM + the 24/40-byte tail; 'R' = the Mac 4.8 route layout read to the end of the record; 'E' of 8 bytes, the 10-byte 'F' tail and the created-by-3 'I' tail are "as expected". | B42 | **Waypoint `<time>` is BaseCamp's creation time (time B, K22), even when it is only the import time.** BaseCamp's own GPX export writes time B as `<time>`; when the imported GPX had no `<time>`, time B is the moment of import, and BCR exports it the same way rather than inventing "no time". **Class-8 waypoint records are route via points**: they are not exported as waypoints (B12, FORMAT.md §5.4 export classes 0 and 1); one that a parsed route point names is counted in the structure dump only, so a library with routes does not show "records this tool does not convert". | 2026-10-07 | mac48 implementation pass |
| B43 | **AllData.gdb's own program version breaks layout ties** (FORMAT.md §3.3 rule 8, §4, §15.11; `chooseLayout()` in `src/format/container.js`, shared by the reader and the structure dump). When more than one layout hypothesis consumes a W, T or R record exactly: program version **408** (Mac BaseCamp 4.8.x, VERIFIED on both samples) and H-MAC48 among them → H-MAC48; **1-407** (an older BaseCamp; the major × 100 + minor encoding is REPORTED for 4.5-4.7 only) and exactly one of H-KBM and H-OP among them → that one; otherwise refused as before. **One more rule, for routes only:** in a 408 file a route that only H-OP decodes is refused, because H-OP's route rule stops before the trailer and a route point count damaged downwards could otherwise be read as a shorter route without a word (96,000 such damaged copies of run1's route: none is shortened in a 408 file; 129 were without the version). The version never picks a layout that did not fit, and a W or T record that one layout alone fits is still used in any file (so the pinned cut-short cases of the verifier pass are unchanged). Effect on real Mac 4.8 output: a route of 0 or 1 via points, which both route layouts fit, is now converted (both read the same via point). The structure dump reports each decision (`tieBreak`: the family in fixed words, counts per layout, routes refused). The `routes` fixture scenario now says 407: it is OP's route layout, and a 408 file with OP routes contradicts the measurement. Reverses §4's "the program version is diagnostic only". | 2026-10-07 | B43/B44 pass (the route-only refusal added here to meet its "no silent shortening" requirement) |
| B44 | **Heart rate and air temperature are exported** (reverses B41's "read but not exported"; FORMAT.md §15.11). TrackSegments slot 7 (heart rate, u8; the one-byte width is a well-supported GUESS, FORMAT.md §15.7) and slot 6 (air temperature, f64) go onto the track's points as the optional `Point.hr` and `Point.atemp` (src/model.js), only where a point holds them and only from a file that matched its track (one to one or through shared endpoints, like elevation). A heart rate of 0 and a temperature that is not finite are absent and counted (`value_treated_as_absent`). The GPX writer writes them as Garmin's **TrackPointExtension v2** (`http://www.garmin.com/xmlschemas/TrackPointExtension/v2`; `atemp` then `hr`, the last child of the `trkpt`; checked against the published XSD on 2026-10-07): an integer 1-255 for `hr` (the schema's `BeatsPerMinute_t`), at most two decimals for `atemp` within -273.15 to 1000 °C; anything else is left out and counted. The root declares `gpxtpx` only when a track has sensor data, decided by the reader's `Track.sensorData` flag so the points are not built twice. **v2, not v1:** BaseCamp's own GPX export writes v1 (testdata/basecamp-real/run2-exports), and v1's sequence begins with the same atemp, wtemp, depth, hr, cad; v2 adds speed, course and bearing and calls itself the replacement. KML is unchanged. The report says once that they were kept (`track_sensor_data_kept`) and counts the tracks. **Cadence is not exported:** no sample holds it and its slot is not measured (FORMAT.md §15.9). | 2026-10-07 | B43/B44 pass (orchestrator) |
