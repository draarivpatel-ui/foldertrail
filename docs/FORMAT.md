# FORMAT.md: Garmin BaseCamp library format, for BCR's reader and its independent fixture writer

Gate 0, corrected after a skeptical review, 2026-10-05.

**§1-§14 were written before any real Mac BaseCamp file had been read.** §15 (H-MAC48) records what real libraries
written by Mac BaseCamp 4.8.13 (made-up content only, 2026-10-07) showed; where §15 and §5-§9 disagree, §15 is the

## 0. How to read this document

**Audience.** An engineer who must implement, from this document alone, either (a) the reader in `src/format/` or (b)
the fixture writer in `tools/fixtures/`, without seeing the other's code or any source listed below. Every byte the writer
emits and the reader accepts is specified in §2 to §9 and §12. Where the sources do not say, this document says UNKNOWN
and gives BCR's rule for that case.

**Conventions**

- All multi-byte integers and floats are **little-endian**. Sizes are in bytes. "var" means variable length.
- A record's **body** is the bytes after its 5-byte frame (§3.2). Offsets inside a record count from the body start.
- `#` numbers in tables are for cross-reference only. Hex such as `4D 73` is in file order.
- "Must be 0 or 1" means: any other value makes the current layout hypothesis fail (§3.3).

### 1.1 Evidence on Mac 4.8 versus Windows 1.88 bytes

No public source shows the bytes of a Mac 4.8 library. All evidence is behavioural, and none of it is byte-level.

**For (weak)**

- JP, thread 64020 (created 2013-07-01, BaseCamp 4.2 era): the Mac library "retains the PC folder structure", and he says
  he *can* import PC folders by replacing the Mac ones. **That is a stated intent; no outcome is reported.** VERIFIED raw
  [K].
- A Garmin representative, thread 95264 (created **2015**-06-25): restoring a Windows backup on a Mac "should work".
  REPORTED.
- MarcE, thread 123502 (created **2017**-01-01): a Windows backup restored on a Mac kept the data but lost track time,
  elevation, temperature and heart rate. REPORTED. GUESS: this matches the Mac Restore bug that skips TrackSegments
  (bobgps 2025, REPORTED), so it says little about byte identity.

**Against**

- **Chris_68, https://www.sorcieremonique.com/t25432-lire-une-base-gdb-dorigine-pc-sur-mac (suggested 2020-08-11,
  reported 2020-08-21):** he copied a Windows 4.7 `AllData.gdb` and `FolderData.gfi` into the Mac 4.8 folder, and
  BaseCamp would no longer start. VERIFIED raw [K]. It is confounded: his Mac library was already corrupt, and he did not
  copy TrackSegments. It is still **the only direct test found** of Windows 4.7 files in Mac 4.8, and it failed.
- Thread 95264 (2015): "Invalid File Format" when restoring a Windows backup on a Mac. REPORTED.
- Thread 64020 (2013): Windows BaseCamp crashed while restoring a Mac backup. VERIFIED raw [K].

**A plausible mechanism for drift (GUESS).** Garmin's Mac change history says "Upgraded app to 64-bit" between 4.7.0
and 4.8.3 (VERIFIED, Garmin download page id=4450, researcher). jpedro (thread t25432) says 4.8 was the build made for
Catalina's 64-bit-only rule (REPORTED). A 32-bit to 64-bit port (LP64 on macOS) is a plausible way for the Mac
serialisation to drift from Windows 1.88.

**Consequence.** The Mac byte check (Gate 1, §13) comes before the record parsers are relied on, not only before
charging. Until then every record parser is provisional, and the structure-only dump (ARCHITECTURE.md §11) is the field
check.

**Reader rules for primitives**

1. **Flags.** A flag byte that is not 0 or 1 makes the current layout hypothesis fail (§3.3). GUESS: OP defines a flag as
   0 or 1 and GB only writes those; KBM would silently accept other values.
2. **Coordinates.** A latitude is in range if −2^30 ≤ v ≤ 2^30 (that is, |lat| ≤ 90°). **Every i32 longitude maps into
   [−180°, +180°)**, so a longitude range check can never fail and rejects nothing. The latitude check rejects about half
   of random values. Real discrimination between layouts comes from exact consumption and the bounds checks (§6.4).
3. **Versions are compared as raw u16 integers, never as strings or floats.** KBM builds the string
   `f"{v // 100}.{v % 100}"` and compares floats (L189-199, L211, L1152-1160) [W1a]. That breaks ordering: 403 and 430
   both become 4.3; 410 becomes 4.1, which compares below 4.3 although 410 > 403; and 109 (1.9) becomes 1.9, which compares
   above 1.79 although 109 < 179. BCR never does this.
4. **Doubles.** An f64 that is NaN or ±Infinity is treated as absent and counted. An altitude or elevation ≥ 1.0e24 is
   treated as absent (GB drops altitudes ≥ 1.0e24, L439 and L886, researcher; BCR extends the rule to TrackSegments, GUESS).
5. **Times.** A present time ≤ 0 is treated as absent and counted (GUESS: GB's writer only writes times > 0, L327-336).
   The i32 overflows in January 2038 (GUESS from the type); times are never interpreted as unsigned.

**Header rules (BCR)**

1. Fewer than 18 bytes, a signature that does not fit the file's role, or a primary format other than 0x0066 → a
   whole-file problem ("this is not a BaseCamp library file"); stop reading that file. For TrackSegments, any signature is
   accepted and recorded (GUESS: probably "MsRc"; Gate 1 check 1).
2. The 'D' record must have length 2 and type 'D'. Otherwise: whole-file problem ("unreadable file header").
3. The 'A' record must have type 'A', L_A ≥ 2, and must fit in the file. The program version is its first 2 body bytes.
   The three cstrs are read inside the body; if they do not end exactly at the body's end, keep the version and count
   "author record not as expected". Reading always continues at offset 18 + L_A. The builder, date and time strings are
   never shown and never go into the dump.
4. The application cstr must end within 64 bytes (GUESS cap; the longest known value has 9 characters). Otherwise:
   whole-file problem. A value other than the three known names is accepted and recorded as "other".

### 3.3 Reader rules and validation contract (BCR)

**Framing**

1. **Always resume at `bodyStart + len`**, however the field parse went. GB does this (VERIFIED), and it confines any
   misparse to one record.
2. A record whose `len` runs past EOF means the file is truncated: stop that file, keep everything parsed so far, report.
3. Unknown type bytes are counted by type byte and never interpreted.
4. **GDB end: read to EOF, and do not stop at 'V'.** OP's order is `W* R* T* G* O* L* j* J* C* V E? X?` (p.12 [W1a]).
   - 'X' is **expected but optional.** OP marks it optional. Evidence that real 1.88 files end with it: KBM's GDB loop is
     `while record_type != 'X'` (L104), and its `read_record` returns `(None, 0, b'')` at EOF (L265-266), so without an
     'X' record that loop would never end. KBM's author reports a completed run (REPORTED), which implies the library had
     an 'X'. Contrast KBM's GFI loop, `while record_type` (L138), which stops at EOF. [K] [W1a]
   - BCR: when an 'X' record appears, stop interpreting; any bytes after it are counted as "data after the end-of-file
     record" and reported. EOF without an 'X' is normal; it is counted in the dump only.
   - GB stops at 'V' (L973-975) [S]. BCR does not.
   - Records out of OP's order are processed anyway; the dump counts order violations.
5. **GFI end:** order per OP p.32 is `F* I* R* T* W* K* J*` [W1a], with no end record. Read to EOF (as KBM L138 does).
6. **TrackSegments** are framed only in the header (§9).

**Layout hypotheses** (W, T and TrackSegments points have several; R had one until §15.11 added H-MAC48 for W, T, R and
the 17-slot TrackSegments point)

7. A hypothesis is **accepted** for a record only if all of these hold:
   - a. it consumes the body **exactly**: no bytes left over and none missing;
   - b. every flag, and every byte this document says "must be 0 or 1", is 0 or 1;
   - c. every count fits before it is used: count × (minimum element size) ≤ bytes remaining, checked before any
     allocation or loop;
   - d. every cstr ends inside the body;
   - e. every latitude is in range (§2 rule 2);
   - f. the record's own checks pass (§5.3 W, §6.4 T, §9.3 TrackSegments).
8. **Evaluate every hypothesis** for the record. Then choose (decision B43; `chooseLayout()` in `container.js`, shared by
   the reader and the structure dump):
   - Exactly one accepted: use it, and count which one in the dump. One exception, for routes only: in a file whose
     program version says Mac BaseCamp 4.8 (408, below), a route that only H-OP decodes is **not** used, because H-OP's
     route rule is the one rule that does not read the record to its end (§7.4, §15.11).
   - None accepted: keep only the agreed prefix and count "details not decoded".
   - More than one accepted: **AllData.gdb's own 'A' record program version breaks the tie**, and nothing else does:
     - **408** (Mac BaseCamp 4.8.x, VERIFIED §15.1) and H-MAC48 is among them: use H-MAC48.
     - **1-407** (an older BaseCamp, Windows or Mac; the encoding major × 100 + minor is REPORTED for 4.5-4.7, OP p.11,
       and a GUESS below that) and exactly one of H-KBM and H-OP is among them: use that one.
     - Otherwise (no program version, 0, 409 and above, or two older layouts that both fit): treat it as none (BCR
       never guesses) and count "matched more than one layout".
   - The dump counts each choice the program version made, and each route it refused.
   - Why the header may decide: every hypothesis in a tie consumed the record exactly and passed every check, so the
     bytes alone cannot choose; the program version is the producer's own statement of which BaseCamp wrote the file,
     and on the two Mac 4.8.13 samples it is 408 in every file while every record is H-MAC48 (§15).
9. A read past the body end fails that hypothesis. Parse failures carry a code, the byte offset inside the record and a
   field number. They never carry a name, a coordinate, a time or a path, and they never throw past the module boundary.
10. Work is bounded: every loop is bounded by a count that was checked against the bytes remaining, so each record costs
    O(len).

## 5. GDB 1.88 'W' (waypoint): agreed prefix, then two hypotheses

(A third, H-MAC48, measured on Mac BaseCamp 4.8.13, is in §15.3 and §15.11. The same holds for 'T' in §6 and 'R' in
§7.)

Fields 1-7 are agreed (OP p.13 and KBM). After field 7 the two sources diverge:

- **H-KBM**: what KBM's working code parses (L475-646) [W1a]. KBM's own docstring (L430-455) copies OP's table; its
  code does something else, which is the sign that it was fitted to real bytes. **This is the hypothesis the supported
  path relies on.**
- **H-OP**: OP's table for file formats ≥ 1.46, with the ≥ 1.54 presence flags (p.13-14) [W1a]. **Status: documented,
  expected not to validate on 1.88.** It stays in the reader because it is cheap and documents the alternative. Its
  fixtures never count as coverage of the supported path (§12).

**Why H-OP is expected to fail on 1.88** [K], recomputed [W1a]

- KBM reads well past the end of OP's record. When every optional field is absent, OP's tail after the icon is 17 bytes
  and KBM's is 33 bytes (§5.2), so KBM reads **at least 16 bytes** past OP's end (18 if all of KBM's 6-byte skip is
  counted as past the end). The skeptic's figure was "at least 22 bytes"; this pass's count from the field tables is 16.
  Either way it is past the end.
- KBM has no guard against short records: `get_uint` returns `None` when fewer than 4 bytes remain (L931-933), and
  unpacking that `None` raises a TypeError (first at L606); `restore_waypoints` (L1644-1676) has no try/except. A record of
  OP's length would have crashed KBM's run. Its author reports that the run completed (REPORTED), so real 1.88 user
  waypoint records are longer than OP's table.

### 9.2 Point

| Field | Type | Size | Rule |
|---|---|---|---|
| elevation (m) | fdouble | 1 or 9 | |
| time | fint | 1 or 5 | |
| N − 2 further bytes | see below | N − 2 | KBM skips them without reading (L1172) |

**KBM's choice of N.** KBM uses N = 11 if the file's own 'A' record program version, after its string-to-float
conversion, is below 4.3, and N = 17 otherwise (L1152-1159). It refuses files whose file format is below 1.79 or whose
program version is below 4.2 in that float form (L1160-1162). That is 9 or 15 extra bytes per point. (The gate-0 dossier
said "11 or 17 bytes"; that was wrong.)

**The same threshold on integers.** Under §2's encoding, KBM's "4.3" is raw 403, but its float conversion maps 403 and
430 alike to 4.3. OP p.11 lists BaseCamp 4.5-4.7 program versions as 4.5-4.7, which is raw 405-407 (REPORTED), so on its
4.7 data KBM used N = 17. The skeptic restated the rule as "≥ 430 → 17"; that does not fit this encoding [W1a]. Either way
the threshold is KBM-only (GUESS), Mac 4.8.x's raw value is UNKNOWN, and **BCR never chooses N by version.**

**Our reading (GUESS).** Each point holds N optional fields, each starting with a presence flag. KBM's fixed skip only
works when fields 3 to N are all absent (one byte each). Users do have heart-rate and temperature data in tracks (MarcE
2017 lost exactly those, REPORTED), and when such a field is present KBM's skip falls out of step.

### 9.3 BCR contract

1. Parse the header (§3.1). Record the signature.
2. Read M. Require M × 11 ≤ bytes remaining (11 is the smallest possible point).
3. For each N in {17, 11}: parse M points. For every point, the elevation and time flags must be 0 or 1, and **each of the
   N − 2 further bytes must be 0** (a 1 means a present field of unknown width; never guess widths). N is accepted only if
   all M points parse and the file ends exactly after the last one. **Superseded for N = 17 by §15.11:** the 15 further
   bytes are presence bytes of slots 3-17, and slots 6 (temperature, f64) and 7 (heart rate, u8) may be present with
   their values; any other present slot still fails N = 17.
4. Exactly one N accepted: use it. Both or neither: the track keeps its positions but gets no elevation or time, and the
   dump records the flag pattern (0 and 1 only), the file length, M, and the file length minus the header modulo M.
5. Match the points to the track (§6):
   - M = Σn: one to one, in segment order.
   - M = Σn − (S − 1) with S > 1: only if, for every segment k > 1, its first position equals segment k − 1's last
     position exactly (KBM's shared-endpoint premise, now checked). The TrackSegments points then map to the sequence with
     those repeated points removed, and each repeated point takes its twin's elevation and time (GUESS).
   - Otherwise: positions only, reported as "elevation and time did not match the track".
   - KBM compares M only with the overlap-removed count (L1711-1713 against L791-793) [W1a].
6. No file for a track's uuid: positions only, with a warning (counted).
7. Elevations and times follow §2 rules 4 and 5.

## 10. Linking the tree to the items

- **Link key:** (record type, **raw name bytes**), plus the class for waypoints. KBM keys on the decoded name only
  (L99-114 [W1a]), so a duplicate name silently overwrites the earlier entry.
- A reference that does not resolve: reported as "listed but not found in AllData.gdb".
- **One item in several lists** is allowed: the Mac manual says "You can include a single item in multiple lists"
  (VERIFIED, researcher). BCR writes the item into each list and reports how many such items there are. In the GFI this is
  simply two reference records with the same name and different parent item IDs.
- **Duplicate names:**
  - GFI references carry no ID or UUID (OP p.32-33 [W1a]). If the GDB holds more than one record with the same key, the
    GFI cannot say which copy belongs where.
  - **BCR does not guess.** All copies go to `_Duplicate names/`, and the report names the lists that referred to that
    name. This rule stays.
  - **The risk is lower than first thought.** GPSBabel's GDB writer forces unique names for waypoints, routes and tracks:
    `set_mustuniq(true)` (gdb.cc L1081), with the name handle reset once per type (L1656, L1665, L1671), the comment
    "unique (!!!) shortname" (L1148), and the calls at L1554, L1571-1573 and L1593-1595. VERIFIED [K] [W1a]. GUESS: GDB
    consumers expect names to be unique per type, so BaseCamp probably renames duplicates on import, and
    `_Duplicate names/` should be rare. Whether a user can still create duplicates by renaming is UNKNOWN (Gate 1
    scenario 2).
  - Whether GFI order matches GDB order is UNKNOWN. BCR does not rely on it.
  - **The lists are named once, on the duplicate group** (`details.duplicates[].listIds`), not on each copy. A copy that
    is also not converted (an unreadable track, say) therefore carries no lists of its own (`listIds: []`): its "Not
    converted" line in the report has no "In: …", and the report's "Duplicate names" section names the lists. (Recording
    every list on every copy made memory grow with copies × lists; library.js.)
- **GDB items with no GFI reference** go to `Not in any list.gpx`. GUESS: normally they hang under the "Unlisted Data"
  item instead.
- **No FolderData.gfi:** there is no tree. Export by type, with a loud warning. SUSSAMB (2020, REPORTED): without the .gfi
  "you'll just get all your data in one list". A 2016 thread (REPORTED) says restoring the matching .gfi brought the lists
  back.

## 11. Text

- **Sources:**
  - GFI list names are UTF-8 (OP p.32 [W1a]).
  - The encoding of GDB 1.88 strings is UNKNOWN. OP says only "either ISO/IEC 8859-1 or UTF-8" (p.3 [W1a]).
  - KBM decodes everything as UTF-8 and drops undecodable bytes (L253, L886 [W1a]); its author's data was German
    (REPORTED via comments).
- **Decoding:** BCR decodes UTF-8 strictly. If that fails, it decodes as windows-1252 and counts the case.
- **Matching:** linking compares raw bytes first. If that fails, it compares the NFC-normalised decoded strings and
  reports each such match.
- **Long names:** folder and list names longer than 255 UTF-16 code units are cut (never inside a surrogate pair) and
  end in "…", counted as the report-level problem `name_shortened` (`MAX_NAME_CHARS` in gfi.js; the 255 is a GUESS:
  BaseCamp's own names are far shorter). A name is repeated in the path of every folder and list below it, so an
  unbounded name would multiply by the number of lists. The message says "characters" although the limit counts UTF-16
  units: a plain-words tradeoff.
- **Output:** characters that XML 1.0 forbids are stripped and counted. File names are sanitised as described in
  ARCHITECTURE.md §6.

The writer lives in `tools/fixtures/`. It reads a JSON scenario and emits a synthetic library. It

**Rule for every scenario: say which hypotheses it exercises.** Scenarios written under **H-OP** (waypoints or tracks)
are labelled "documented hypothesis, not supported-path coverage". They exist to prove the reader can tell the
hypotheses apart. A test report must not count them towards coverage of the supported path, which is defined by H-KBM
(§5, §6) and the single TrackSegments layout (§9).

- Vary the program version across scenarios (for example 402, 407, 408, 480, 4813): the reader must not branch on it.

**AllData.gdb:** header, then W*, R*, T*, then V (`02 00 00 00 56 00 01`), E and X (§3.2). Variants: no 'X' (EOF after
'E'); bytes after 'X'; a 'V' followed by more W records; a record whose `len` runs past EOF; an unknown record type.

**W records**
- H-KBM (supported path): every optional field absent (the 33-byte zero tail); altitude present; K18 only, K22 only and
  both times; non-empty address cstrs; K13 with b = 1 and 24 opaque bytes; phone count 1; links; categories; non-zero
  opaque bytes in K19 and K23 (the reader must ignore them).
- H-OP (not coverage): the 17-byte zero tail; colour ≠ 0; links; thumbnail present. The Subclass1 and Subclass2 present
  flags can only be 0, because their sizes are UNKNOWN.
- Negative cases: H-KBM phone count 2 (must not be accepted); a flag byte of 2; a record one byte short; a record one byte
  long; classes 0, 1 and 8.

**T records**
- H-KBM (supported path): gaps of zero bytes and of non-zero bytes; one segment; several segments with shared endpoints
  and without; an empty segment; tight and loose bounds; S = 0.
- H-OP (not coverage): the same shapes without the gaps.
- Negative cases: a point outside its segment's bounds; segment bounds outside the track bounds; min > max; a bad uuid;
  a total point count that matches neither rule (must still be accepted, §6.4 g).
- UUIDs come from a seeded PRNG.

**R records:** route points with A = 0 and link points; a point with L = 0 that resolves by name; one that names a
duplicate; one with A > 0 followed by junk, where the reader must stop cleanly; a bad Unknown7. Trailer: links 0, colour 0,
autoroute flag 0, empty notes, filtered flag 0, filtered count 0, Unknown10 = 1, Unknown11 = 0, activity profile 0.

**FolderData.gfi:** header ("DifG"), then F records (root 0xFFFFFFFF first), I records, then T, W, R and K references;
no end record. Scenarios: a nested folder > folder > list tree (depth ≥ 3); a list directly under the root; lists with
created-by 0 (no tail), 1 and 8 (with the 9-byte tail); one item referenced from two lists; duplicate names; a dangling
reference; a folder cycle (negative); F and I tails missing or extra.

**TrackSegments/<uuid>:** header, then a bare u32 M, then each point: fdouble elevation, fint time, then N − 2 zero
bytes. Variants: N = 17 and N = 11; mixed present and absent elevation and time; one extra byte set to 1 (no elevation or
time expected); M not matching the track; M matching the overlap-removed count with identical shared endpoints and with
different ones; trailing bytes.

**.Backup:** a ZIP built with `node:zlib` deflateRaw, independent of the browser's DecompressionStream path. Paths
`BaseCamp_x/Database/4.8/…`. Variants: stored, deflated, and ZIP64.

**H-MAC48 (§15, §15.11; supported path):** W records with the H-KBM tail plus 8 opaque bytes (zero and non-zero),
with an address, a phone, both times, and class 8 route via points; T records with the 24-byte tail (no elevation) and
the 40-byte tail (both fdoubles present), flag bytes 0 and 1; R records in the Mac 4.8 layout (link points [this via
point, next via point], the last via point with L = 0 resolving through its class-8 W record, the 19 zero bytes, the
trailer with colour, Unknown10 = 1, activity profile 6 and the 10 bytes); 'E' of 8 zero bytes; F records with the
10-byte tail; I records with created-by 3 (5-byte tail, smart lists that reference every item) and 8; TrackSegments
17-slot points with temperature (slot 6) and heart rate (slot 7). Negative cases: an H-MAC48 W one byte short; a
track flag byte of 2; a non-zero byte in a route point's 19-byte run; a route with the autoroute-settings flag 1; a
TrackSegments point with an unknown slot (for example 9) present.

**Content:** all names, coordinates and times are synthetic. Scenarios include sentinel strings and numbers for the
privacy test (ARCHITECTURE.md §11).

**Limit:** these fixtures prove that the reader matches *this document*. Only Gate 1 can show that this document matches
BaseCamp.

### 15.10 Consequences for the reader (as found by the derivation pass; implemented under §15.11)

- **W:** before H-MAC48, no Mac waypoint was accepted (H-KBM is 8 bytes short, H-OP fails). Add H-MAC48 = H-KBM plus the 8-byte
  end, and export time B (creation) as `<time>`, as BaseCamp does.
- **T:** add the tail (3 bytes, 11 flag bytes, fdouble, fdouble, 8 bytes) after the UUID. Today H-KBM finds the UUID but
  fails exact consumption, so no track is decoded or linked.
- **R:** per point, 19 bytes after the marker; no 3-byte Unknown1 before the bounds flag; 10 bytes after the activity
  profile.
- **TrackSegments:** walk 17 presence slots with the widths in §15.7 instead of a fixed N; stop on a present slot of
  unknown width.
- **GFI:** F tail of 10 bytes; I tail by created-by (0: none, 3: 5 bytes, 8: 9 bytes).
- **Product questions (not format):** the smart lists "Last Week" and "Last Month" reference every recent item, so
  exporting every list writes everything up to three times; class-8 via points are in no list; waypoints without a GPX
  time carry the import time as their creation time, and BaseCamp exports that as `<time>`. Decided in §15.11 and
  DECISIONS B40-B42.

### 15.11 Reader contract for H-MAC48 (BCR)

H-MAC48 is a **third layout hypothesis** next to H-KBM and H-OP, for 'W', 'T' and 'R' records and for TrackSegments
points. §3.3 rules 7-10 apply: every hypothesis is evaluated; one that consumes the record exactly and passes every
check is "accepted"; exactly one accepted → use it; none → agreed prefix only; more than one → AllData.gdb's program
version breaks the tie (408: H-MAC48; 1-407: the one older layout that fits), otherwise none, counted (§3.3 rule 8,
B43). H-MAC48 is part of the supported path for file format 188 (B41) whatever the program version: a record that only
H-MAC48 fits is used in any file. Field labels below are §15's row numbers ("15.3 row 22" and so on).

**'W' (H-MAC48)** = the agreed prefix (§5.1), then H-KBM's tail K8-K24 with every H-KBM rule of §5.3 (K13's b and stop
byte 0 or 1; K20 phone count 0 or 1; every fdouble and fint flag 0 or 1), then **8 opaque bytes** (§15.3 row 23's last
8; never checked, counted in the dump only as zero or non-zero), then the end of the body.

- The category count stays where H-KBM reads it (after K23's 3 bytes): a GUESS (§15.3 row 23).
- Minimum tail after the icon: 41 bytes (H-KBM's 33 + 8). H-MAC48 is H-KBM plus exactly 8 bytes, so the two can never
  both consume a record exactly.
- Export, as H-KBM (§5.4): altitude from K14; time = K22 (time B, BaseCamp's creation time) if present, else K18. On
  Mac 4.8, K22 holds BaseCamp's **import time** when the imported GPX had no `<time>`; BCR exports it, as BaseCamp's own
  GPX export does (B42).
- **Class 8** is a route via point (§15.3 row 2). It is not exported as a waypoint (§5.4 exports classes 0 and 1). A
  class-8 (or any not-exported class) W record whose raw name and class a parsed route point names is counted only in the
  dump ("route via point record"); other not-exported classes keep the report-level count of §5.4 (B42).

**'T' (H-MAC48)** = H-KBM through the uuid (§6.1 rows 1-17, with G1 and G2, and every §6.4 check), then the Mac 4.8
tail, then the end of the body:

  via point]); otherwise the W record of the same raw name and class, if exactly one exists (on Mac 4.8 the last via
  point, through its class-8 W record).
- **Combining the route hypotheses** (§3.3 rule 8, B43). H-OP (§7.4) and H-MAC48 are both tried, and the layouts that
  decode the route are chosen from like any other record's:
  - only H-MAC48: use it, in any file;
  - only H-OP: use it, **except in a file whose program version is 408** (Mac BaseCamp 4.8), where the route is not
    converted ("its record could not be decoded"; the dump counts "matched only the older route layout in a file
    written by BaseCamp 4.8 for Mac");
  - both: 408 → H-MAC48; 1-407 → H-OP; anything else → not converted, counted as matching more than one layout;
  - neither: if H-OP stopped at an autoroute count A > 0, the route is "road-following" as before (§7.4), in any file;
    otherwise it is "could not be decoded". H-MAC48 never reports a route as road-following: it cannot tell.
- **Why both fit a Mac 4.8 route of 0 or 1 via points** (measured on synthetic routes and on run1's route cut down to
  one of its own via points): H-OP does not read the trailer, so it takes the first 6 of the 19 zero bytes as its own
  fields and reads bounds from what follows. Both layouts read the via point the same way (name, class, link points),
  so whichever the program version picks, the route is the same; on run1's route cut down to each of its four via
  points, 408 and 407 give the same point (test/real-basecamp-mutations.test.js). With 2 or more via points H-OP falls
  out of step on the second point and only H-MAC48 decodes (checked on routes of 2-6 points with names of 0-13
  characters). A two-point record can still be built that both fit (the independent reviewer's 166-byte construction, re-built
  and VERIFIED; with 408 it is now read as H-MAC48, without a program version it is still refused).
- **Why H-OP alone is refused in a Mac 4.8 file** (verifier pass, 2026-10-07; constructed damage, not seen in BaseCamp
  output). Because H-OP stops before the trailer, a Mac 4.8 route whose point count was damaged downwards (say 4 → 1)
  could be read by H-OP alone with the later via points silently dropped, when the bytes it then reads as route bounds
  held valid latitudes (on run1's route: the next via point's third character changed to a space, a digit or any byte
  below 0x40). Under B43 that route is refused in a 408 file: with every byte of the next via point set to each of its
  256 values, for each count of 0-3 (96,000 damaged routes), none is read as a shorter route; the same damage read
  without a program version shortens 129 of them (VERIFIED, test/real-basecamp-mutations.test.js). In a file from an
  older BaseCamp, or with no program version, H-OP's rule is unchanged, because there H-OP is the route layout; making
  H-OP read OP's §7.3 trailer to the end would close the same gap for those files, but that trailer is single-source
  and was never seen in a real Windows file, so it is not done.
- **Cut records (verifier pass).** A Mac 4.8 'W' or 'T' record whose body is cut back by exactly the H-MAC48 tail (8
  bytes; 24 or 40) is read under H-KBM with the same values. Three timed waypoints of run1 cut by 28 bytes are read under
  H-OP with **other** values (elevation and time from the wrong bytes). Each needs the record's length field and its
  body changed together; pinned in `test/real-basecamp-mutations.test.js`. B43 does not change these: for 'W' and 'T'
  the program version only breaks ties, and a record that one layout alone fits exactly is still used in any file
  (refusing H-KBM and H-OP outright in a 408 file would also refuse the cut-by-8 case, whose values are right).

**TrackSegments: the 17-slot point replaces §9.3 step 3's N = 17.** A point is 17 presence bytes in order, each 0 or 1,
each followed by its value when 1: slot 1 elevation (f64), slot 2 time (i32 Unix seconds), slot 6 air temperature
(f64), slot 7 heart rate (u8; the width is a GUESS, §15.7). A 1 in any other slot (3-5, 8-17) fails the point size,
because its width is unknown. With slots 3-17 absent, a 17-slot point is byte for byte §9.2's N = 17 point with its 15
further bytes 0, so every file the old N = 17 accepted is still accepted. N = 11 (9 further bytes, all 0) stays the
other point size; exactly one of the two must fit (§9.3 step 4). **Air temperature and heart rate are exported**
(decision B44; until then they were only read to stay in step, B41):

- They go onto the track's points with elevation and time, by the same match (§9.3 step 5: one to one, or through
  shared endpoints, where the repeated point takes its twin's values), and only from a file that matched its track. A
  file that decodes but does not match its track gives nothing, and that mismatch is what the report says.
- A point gets each value only where its slot is present. A present heart rate of 0 is absent (no heart beats 0 times a
  minute, and Garmin's schema starts at 1) and a present temperature that is NaN or infinite is absent; both are counted
  with the other impossible values (`value_treated_as_absent`).
- The GPX writer puts them in Garmin's TrackPointExtension v2 (`gpxtpx:atemp`, then `gpxtpx:hr`, the last child of the
  `trkpt`; namespace `http://www.garmin.com/xmlschemas/TrackPointExtension/v2`, element names and order read from the
  published XSD on 2026-10-07). BaseCamp's own export writes the v1 namespace (§15.7: `gpxtpx:atemp`, `gpxtpx:hr`);
  v1's sequence begins with the same atemp, wtemp, depth, hr, cad. KML is unchanged and holds neither.
- The report says so once, counted per track that kept either (`track_sensor_data_kept`).
- **Cadence is not exported**: no sample holds it, and which slot (if any of 3-5 and 8-17) carries it, and how wide it
  is, is not measured (§15.9). A present slot of unknown width still fails the point size, so such a track keeps its
  positions only, as before.

**'E'**: 4 bytes (OP) or 8 bytes (Mac 4.8), all 0. Nothing is read from it; the dump counts which.

**'F' tail** after the children: **1 byte** (OP) or **10 bytes** (Mac 4.8: u8, u32, i32 time, u8) are both "as
expected"; any other length counts `folder_tail_unexpected` (dump only). The tail's values are never used.

**'I' tail**: none when created-by is 0; OP's 9 bytes (u8 1, u32 1, u32 9) for any other created-by (measured on
created-by 8); and, for created-by 3 only, the 5 bytes u8 1, u32 0 (measured). Anything else counts
`list_tail_unexpected` (dump only). (One reading fits both measured tails, u8 1, u32 N, N × u32, but only N = 1 with
the value 9 and N = 0 were seen, so BCR accepts only those.)

**Smart lists (B40).** An 'I' record with **created-by 3** is a smart list: a list BaseCamp fills by itself from rules.
On Mac 4.8.13 the two in run1 are "Last Week" and "Last Month", which BaseCamp made without being asked; Garmin's Mac
manual also lets users make their own with File > New Smart List from "user-defined rules" (VERIFIED: the manual page
"Smart Lists", read 2026-10-07). Whether a user-made smart list is also created-by 3 is UNKNOWN (§15.9). Both smart lists
in run1 have the same 5-byte tail although their rules differ, so the rules are not in the tail (GUESS: they are stored
elsewhere). In the GFI a smart list holds an ordinary item reference for every item it showed when BaseCamp last saved.
BCR does not export a smart list as a list:

- it is left out of the tree (in run1 it hangs directly under My Collection and has no children, so nothing else moves);
- its item references place nothing; an item that only smart lists name goes to "Not in any list";
- the report says once that smart lists were left out and that their items are saved in the user's own lists or in
  "Not in any list" (counted per smart list, `smart_lists_left_out`).

The created-by value decides, never the list's name (GUESS: the names are translated in other languages). Created-by 8
("Unlisted Data") stays an ordinary list (§8.4).

## Appendix A: GDB 1.7/1.8/1.9 (GB-backed, reference for a later version)

This appendix is VERIFIED by the gpsbabel researcher from GB at 7003cff. GB's test suite reads
`reference/gdb-sample*.gdb` (not copied into this repository; GPL).

**W record**, all fields in order:
1. name (cstr)
2. class (u32)
3. country code (cstr)
4. subclass (22 bytes: i32 map segment ID, i32 map object ID, 8-byte subclass 1, u16 subclass 2, i32 subclass 3)
5. position
6. fdouble altitude
7. comment (cstr)
8. fdouble proximity
9. u32 display
10. u32 colour
11. u32 icon
12. city, state, facility (3 cstr)
13. u8
14. fdouble depth
15. Version-dependent block:
    - 1.7/1.8: street cstr, fstring, u32 leg time, cstr directions, cstr link (GB writes 7 zero bytes + cstr, L1187-1201);
    - 1.9: street cstr, fstring, u32 leg time, cstr directions, u32 n + n × cstr links.
16. u16 category bitmask
17. fdouble temperature
18. fint creation time
19. 1.9 only: u32 phone count + (cstr, fstring) each, then cstr country, cstr postal code

Line references: L401-638 (read) and L1148-1258 (write).

**R record**
- Header: cstr name, u8 auto-name, u8 no-bounds flag (+ bounds with altitudes), u32 count.
- Each point:
  - cstr name, u32 class, cstr country, 22-byte subclass;
  - an fstring that GB reads as a fixed skip (disagrees with OP);
  - 18 bytes;
  - u32 n link points × (position, fdouble altitude);
  - bbox;
  - ≥1.8: 8 × FF;
  - 1.9: 2 bytes. GB assumes both fint flags are 0.
- Trailer:
  - 1.7/1.8: cstr link;
  - 1.9: links, u32 colour, u8 autoroute flag + block (L815-841), cstr notes.
- A point with 0 links is resolved by name against W records (L763-777).
- Line references: L642-856 (read) and L1272-1406 (write).

**T record**
- cstr name, u8 display, u32 colour, u32 n
- n × (position, fdouble altitude, fint time, fdouble depth, fdouble temperature)
- links: a cstr in 1.7/1.8; u32 n + cstrs in 1.9
- Line references: L860-915 (read) and L1414-1450 (write).

**Known GB/OP disagreements in 1.7-1.9:** route-point Unknown1, the 1.9 waypoint fstring, the 1.7/1.8 waypoint middle
block, phone numbers, the autoroute avoidance counts, speed units, and the 1.9 route-point end time. Because records are
length-prefixed, each misparse stays inside one record.
